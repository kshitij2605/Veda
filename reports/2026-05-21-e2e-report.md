## Ranked improvement suggestions (remaining after all fixes)

### P1 (block real-world adoption)

1. **Document the explicit `commit_ts` encoding** (Hlc = `(physical_ns << 32) | logical`) in the OpenAPI spec for `?at=`. Today users send wall-clock micros/millis and get "no records" silently. Add an `?at=now-1h` shorthand. Effort: ~half day.
2. **Insert response should always return `ids` (not just on log-primary path).** Affects any downstream test/script that needs to GET-by-id immediately after insert. Effort: ~1 hour.
3. **`split_sentences` should recognize `。` (CJK full-stop)** and other Unicode sentence-ending punctuation. Currently only recognizes ASCII `.?!\n`. Effort: ~2 hours.

### P2 (DX / observability)

4. **/v1/admin/metrics labels** — `default__{collection}` prefix is exposed in Prometheus labels. Niriksha and other consumers have to strip the prefix. Either drop it from the label or surface a separate `tenant` label. Effort: ~half day.
5. **Compaction timeout under sustained insert load.** The 24h soak showed insert failures (2.6%) starting at ~11k records, accelerating toward the end. Compaction runs frequently and occasionally causes insert timeouts. Consider: background compaction on a separate thread, or raise the insert timeout. Effort: ~1 day.
6. **RSS grows linearly with record count on non-log path.** The soak showed 474 MB → 1,257 MB over 24h (~9,700 new records). This is by-design (records live in-memory on the non-log path) but means the non-log path cannot scale past available RAM. Document this limit and recommend `use_log_primary: true` for collections exceeding ~100k records. Effort: ~half day (docs + advisory).

### P3 (scale headroom — not measured this session)

7. **Bench the full index matrix on ≥ 100 k records.** This session was capped at 2409 because that's the rag-anything corpus size. The HNSW / IVF-PQ / DiskANN / RaBitQ family won't show their wins until L3 spills. Useful before any v1 GA claim.
8. **MVCC GC under a hot-write workload.** The 24h soak showed RSS growth proportional to record count; analyse whether MVCC GC is actually reclaiming old versions or retaining them indefinitely.
9. **Multi-node cluster test.** Single-node weakly exercises BookKeeper-style replication, FollowerHealthMonitor, WAN shipping, promote-replica. Needs a dedicated 3+1 deployment.

## Validated assumptions / what works well

- **Recovery from disk:** stopping veda-server (kill -9) and restarting cleanly re-loaded all 5 test collections including their sealed segments. Zero data loss across the bench.
- **Semantic quality on Japanese queries** is excellent — the BGE-M3 embedding + Veda's HNSW returns the correct vendor doc at top-1 on every query in the eval set (Microsoft license → MSライセンス doc; ランサムウェア → AppCheckPro doc; PowerBI → PowerBI doc with 0.378 distance).
- **HNSW + BM25 + RRF hybrid** gives the expected latency = dense + sparse + small fusion overhead (~6.6 ms p50 client end-to-end including embed RTT).
- **Adaptive router** (`/v1/route`) returns sensible LLM-backed strategy suggestions per query.
- **Atomic reindex primitive** works (sibling `name@v2` created in 0.1 s for the 2409-record corpus after the chunker fix landed).
- **Percolator txn** begin → commit returns 200 with `commit_ts_ns` in the response.
- **Server stays alive under reindex / insert / search load** after the two P0 fixes. Soak monitor will validate this for 24 h.

## 24h soak analysis (completed 2026-05-22)

The Python soak script (`/tmp/veda_soak.py`) ran for exactly 24h against the test server on port 6341.

| Metric | Value |
|---|---|
| Duration | 24h 0m 4s |
| Total iterations | 48,640 |
| Insert attempts | 9,728 (1 in 5) |
| Insert failures | 257 (2.6%) |
| Search attempts | 38,912 (4 in 5) |
| Search failures | **0** (0.0%) |
| Records at start | 3,338 |
| Records at end | 13,037 |
| RSS at start | 474 MB |
| RSS at end | 1,257 MB |
| RSS growth rate | ~80 MB/h (linear with record count) |
| FD count | Stable 10-11 |

**Insert failures**: Started at iter=39,000 (~11k records, ~1 GB RSS), accelerated toward the end. All failures were insert-side; the server log shows frequent "compaction completed" messages in the final hour, suggesting compaction contention is the root cause. Search remained 100% reliable throughout.

**RSS**: Growth is proportional to record count (~80 bytes overhead per record in the in-memory store). This is expected on the non-log path where `ClusterStateMachine.records` is the data store. Not a leak — it's data accumulation. The log-primary path (`use_log_primary: true`) would not exhibit this because records live on disk.

**FDs**: Rock-solid at 10-11 throughout. No file descriptor leak.

**Verdict**: No memory leak, no fd leak, no search degradation. The only concern is insert timeout under compaction pressure at scale, which is a known limitation of synchronous compaction on the insert hot path.
