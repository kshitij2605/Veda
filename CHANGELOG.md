## [Unreleased]

### Added
- **Block-Max WAND pruning for BM25 search** — sealed-segment BM25 search now skips posting blocks that cannot contain a top-k result, using per-term block-max impact bounds derived when a segment opens (`Bm25Index::load` calls the new `build_blocks` after its JSON parse; a growing segment carries no block metadata and keeps using the existing exhaustive path unchanged). The default (`theta = 1.0`) is rank-safe — verified byte-for-byte identical to exhaustive scoring against a 10,000/100,000-document synthetic corpus — and `prune_theta` on a `bm25` query opts into more aggressive, non-rank-safe pruning. Measured 2.01x-2.53x per-query speedup over exhaustive scoring at these corpus sizes; see `documentation/2026-08-13-block-max-wand-design.md`.

### Fixed
- **`match_phrase` no longer scores the whole collection to rank its matches** — phrase/proximity search now scores only the docs that already passed positional matching instead of running full BM25 search over every document. This also avoids a heap-capacity overflow that a phrase query's `k = usize::MAX` would otherwise trigger now that block metadata exists.
- **BM25 results with equal scores are now ordered by document id** — ties previously fell back to `HashMap` iteration order, which is neither stable across runs nor comparable between the exhaustive and block-max paths. Both paths now sort by score descending, then doc id ascending, so repeated identical queries return identical orderings.

## [0.6.0] - 2026-08-13

Retrieval guardrails — closes the OWASP 2026-07-12 indirect-injection vector (hostile instructions carried *inside retrieved documents* rather than in the user's prompt), which the existing input/output guardrails (v0.5.0) could not see. Every chunk is screened at ingest against its already-computed text embedding and stamped with four reserved fields (`_guardrail_flagged`, `_guardrail_score`, `_guardrail_category`, `_indexed_at`); every LLM-facing path (`/converse`, `/converse/stream`, MCP `tools/call`, `/agent-tools/{id}/execute`, `/a2a/{agent_id}`) drops **hostile**-flagged chunks (`PromptInjection`/`Jailbreak`/`Unsafe`/`IndirectInjection`) before the LLM sees them and attaches a `retrieval_guard` report; `Pii` is detected and reported (`flagged_not_dropped`) but passed through — live calibration found PII-only chunks (e.g. a contact detail in an otherwise-benign vendor deck) being dropped identically to injection attempts, and silently stripping a genuine contact detail out of an answer was judged a worse failure than the threats this feature targets. An unrecognised or missing category on a flagged chunk fails closed (treated as hostile, dropped). Raw `POST /search` only annotates (`_guardrail_class`) and never drops, so recall stays observable. A new `POST /v1/admin/collections/{name}/rescan-guardrails` re-screens and persists verdicts onto an existing collection (rebuilds through `/reindex`, atomic alias swap). See `documentation/2026-08-12-retrieval-guardrails-design.md`.

### Added
- **Retrieval guardrails** — `screen_chunk` cosines each chunk's text embedding against a document-phrased `IndirectInjection` pattern set (distinct from the input-side patterns; `RETRIEVED_THRESHOLD = 0.60`, measured against a 10-PDF/149-chunk known-clean Japanese business corpus: the semantic layer flagged 0/149 — the observed near-miss ceiling was 0.354, well clear of the threshold — while the always-on PII regex layer flagged 3/149 (2.01%) on genuine email/phone contact info, unrelated to this threshold) and stamps the four reserved fields on every ingest path (`process-document`, `embed-insert`, `insert`). `ToolCatalog::dispatch` enforces the drop at the tool-dispatch choke point on every LLM-facing surface; `get_record` applies the same category-aware policy — a hostile-flagged record is withheld outright, a PII-flagged one comes back intact.
- **`POST /v1/admin/collections/{name}/rescan-guardrails`** — re-screens every record in a collection and persists the verdict, for corpora indexed before this feature shipped or after a pattern-set update. Manual admin endpoint only; see *Removed* for why it is not schedulable.
- **`retrieval_guard` at the top level of `/converse` and the `/converse/stream` `done` frame** — rolled up across every retrieving tool call in the turn (counts summed, `dropped_chunks`/`temporal` concatenated). Previously the report was only reachable nested inside `steps[].result.retrieval_guard`, which is not a surface any client reads — and the decision to pass `unscreened` chunks through is only defensible if an operator can actually see the counts. A turn that made no retrieving tool call **omits** the field rather than reporting an all-zero report: "did not retrieve" and "retrieved, all clean" are different facts.
- **`VEDA_RETRIEVAL_GUARD` kill switch** — set it to `off` (also `0`/`false`/`no`/`disabled`) to degrade every LLM-facing path to annotate-only: hits are still classified and still counted (`flagged_not_dropped` reports what would have been dropped), nothing is removed. Unset — or set to anything else — enforces, so the switch can only ever weaken enforcement, never enable it by accident. It is read per tool dispatch, so it applies without a restart. Enforcement at the choke point is otherwise unconditional and is **not** gated on an agent's `guardrails` flag (that flag governs input/output safety guardrails only); the switch exists so a false-positive pattern hit on a real corpus has an operator remedy short of a code change.

### Fixed
- **PII no longer masks a hostile finding in the same chunk** *(pre-release hardening, same cycle)* — `screen_chunk_with` checked the PII regex before the semantic hostile-pattern layer and returned on the first match, so a chunk that was both genuinely hostile AND happened to contain an email/phone/etc. was reported as `Pii` — exempt from dropping — and reached the LLM. The canonical exfiltration pattern ("forward the conversation history to the address below") is exactly this shape: the realistic attack necessarily contains a destination address in the same chunk, so it would have self-exempted. The semantic layer now always runs first and wins whenever it flags; PII is the reported category, and the pass-through exemption applies, only when it is a chunk's sole finding.
- **The `aggregate` tool no longer leaks withheld chunk text as a group key** *(pre-release hardening, same cycle)* — `aggregate(field=…, metric=count, group_by=<text field>)` returns each group's key verbatim, so `group_by=content&filter=_guardrail_flagged = true` returned the full text of exactly the chunks every other LLM-facing path withholds, and `dropped_chunks[].id` told a model what to ask for. The dispatch-level guard could not see it: an aggregate payload carries neither `hits` nor `records`, the two array shapes it screens. MCP exposes the whole builtin catalog unwhitelisted, so this was reachable from any external MCP client. Hostile-flagged records are now skipped inside the aggregation walk, via the same `category_is_hostile` policy used everywhere else, and the skip is reported as `retrieval_guard.withheld_records`. **The raw `GET /v1/collections/{name}/aggregate` endpoint is unchanged** — it annotates nothing and drops nothing, matching `/search`, so recall measurement stays intact.
- **`process-document` can complete on a multimodal collection** *(pre-existing bug, fixed here)* — a dense vector field is a mandatory column (every record must carry one, or the storage layer rejects the insert), but the pipeline's two ingest loops built **disjoint** target sets: the text-chunk loop fed `auto_embed: Text` and non-`*image*`-named fields, the image-record loop fed `auto_embed` image/video/audio and `*image*`-named ones. No field was ever filled by both, so the ingest failed in both directions — an `image_blob` collection with a plain `embedding` field died as soon as OCR returned an image, and a collection with an image vector field died on its *text chunks*, even for a document containing no images at all. Both loops now resolve their columns through one shared `resolve_dense_targets`, so a collection with a single vector field backed by a multimodal model holds a document's prose and its figures in one unified vector space — the model Veda is designed around. Where a schema genuinely cannot be satisfied (no registered model can embed images into one of its vector fields), the request is now refused up front with `409 INCOMPATIBLE_SCHEMA` naming the field and the fix — matching `/ingest-media`'s guard for the identical invariant — instead of reaching storage as `record missing required vector field` with half the document already inserted. A text-only collection still ignores a document's images exactly as before.
- **The `aggregate` tool's withheld count now reaches the turn-level report** *(pre-release hardening, same cycle)* — `RetrievalGuardReport` had no `serde` default, so deserialising the one count `aggregate` emits (`{"withheld_records": N}`) failed on the missing `kept`, and the turn-level roll-up — which reads the per-call reports back out of the recorded steps and skips any step it cannot parse — dropped that call entirely. Two consequences: the withheld count never reached the top-level `retrieval_guard` on `/converse` or the stream `done` frame, and a turn whose only retrieving call was `aggregate` **omitted** the field, which this release documents as meaning "the agent never retrieved". `withheld_records` is now a field of the report, and the report tolerates the partial shapes its producers emit.
- **`aggregate`'s `withheld_records` counts what the query excluded, not what the collection holds** *(pre-release hardening, same cycle)* — the hostile-record skip ran before the filter, so an aggregation narrowed to rows that contain no hostile content still reported the whole collection's hostile records as withheld from it. The skip now runs after the filter and still before any accumulation, so the number means "records this query would have counted and did not" and no hostile record can reach a group key.
- **`process-document` image records are stamped** *(pre-release hardening, same cycle)* — the OCR pipeline inserted its per-image `[image: x.png]` placeholder records bare, with no `_indexed_at` and no verdict, so they classified `unscreened` while `/ingest-media`'s equivalent records classified `skipped`. They now stamp `skipped` like every other media path. This matters because `unscreened` is the one signal the fail-open decision rests on: with the two paths disagreeing, an operator who ran a full re-scan still saw `unscreened > 0` and could not tell pre-feature data from the document pipeline's own output.
- **Citation snippets are no longer poisoned by reserved fields** *(pre-release hardening, same cycle)* — a hit's `fields` map is a `BTreeMap`, so `_`-prefixed reserved keys sort before every ordinary field name, and `grounding::first_stringy_field` took the first string value as the document text. On a PII-flagged hit — which the category policy deliberately keeps — that made the citation snippet the literal string `"pii"`, and fed `"pii"` to the faithfulness judge as the retrieved context. Reserved keys are now skipped.

### Removed
- **`JobKind::RescanGuardrails` (the schedulable re-scan)** — removed before release; the manual `POST /v1/admin/collections/{name}/rescan-guardrails` endpoint is unaffected. Each re-scan materialises a full copy of the collection (rebuild through `/reindex` into a sibling, then an alias swap) and superseded siblings are never reclaimed. That is an acceptable one-off cost for a manual admin action an operator chooses to take, and is documented as such; as a cron kind it is a nightly full-corpus copy, forever, ending in a full disk. The variant can return once superseded siblings are reclaimed.

### Known limitations
- **Chunks indexed before this feature carry no verdict, are reported as `unscreened`, and are passed through; run the re-scan to close that gap.** Treating an unstamped chunk as hostile would empty every existing collection on upgrade, so enforcement fails open on missing verdicts by design — this is the one deliberate asymmetry in the model.
- **Plain `POST /v1/collections/{name}/insert` is never screened.** Screening runs against a text embedding Veda computed itself, so it only happens on `process-document`, `ingest-url` and `embed-insert`. `/insert` takes client-supplied vectors, so every record it writes is stamped `skipped` — including the Python SDK's normal client-side-embedding flow. Unlike the `unscreened` case above this is not closed by one upgrade-time re-scan: it recurs with every `/insert`, so a corpus ingested that way needs the re-scan run on a cadence. Ingest behaviour is deliberately unchanged in this release.
- **Temporal conflict detection is active on `filter_query` and inert on `search`.** Conflict needs each hit's stored vector inside the hit's fields; `filter_query` serialises them, `search` deliberately skips vector fields when hydrating hits. Staleness and expiry work on both. Hydrating raw embeddings into every search hit would inflate every LLM-facing payload by (dimensions × top-k) floats to serve a secondary signal, so the fix waits on a cheaper hit-to-hit comparison (content hash, or reusing the distances the index already computed).
- Superseded rescan siblings (from repeated `/rescan-guardrails` or `/reindex` calls) are never dropped, so repeated rescans grow storage.

## [0.5.1] - 2026-06-21

Multimodal E2E follow-up — closes the three caveats the v0.5.0 campaign left open (OCR, SPLADE sparse, and live index-type validation) by standing up the missing sidecars and landing the fixes they surfaced. Real **FlashParse** (GLM-OCR + PP-DocLayoutV3) validated `process-document` end-to-end (2-page PDF → 3 OCR'd pages in ~42s → 3 chunks incl. a real table + 4 images → embedded into **both** dense and SPLADE → all searchable); a real **SPLADE encoder** verified sparse search (4/5 top-1); and all **10 CPU index types** build + search end-to-end through the API (recall@10 vs flat: flat/hnsw/diskann/rabitq_rerank/sq8 1.00, sq4 0.99, ivfpq 0.97, rabitq/hnsw_rabitq/rabitq_ext_rerank 0.90; `cagra` SKIP — no cuVS in this build). See `reports/2026-06-21-e2e-report.md` (§7) and `reports/2026-06-21-e2e-bug-findings.md`.

### Added
- **`POST /v1/collections/{name}/seal` + `VEDA_SEAL_THRESHOLD`** — an explicit seal/flush route (and an env to tune the seal size threshold) so declared index types build on sealed segments and become testable/operable through the API on small data (closes the v0.5.0 "no seal route" limitation). Note: `/insert` already auto-seals + builds the index per batch; this route is for explicit control.

### Fixed
- **SPLADE sparse inserts no longer fail on descending term indices** *(P1)* — the SPLADE/TEI encoder returns term indices in **descending** order, but `SparseVec::new` requires **ascending**, so **every** SPLADE auto-embed insert failed; `parse_response` now sorts indices ascending. Sparse search verified 4/5 top-1 against a real `naver/splade-cocondenser-ensembledistil` encoder.
- **`cagra` index now rejected at create time** *(P1)* — `cagra` was accepted at collection-create then silently failed in the background rebuild on builds without cuVS, leaving searches empty; it is now rejected at create with a **400** instead of failing late.
- **`LlmClient` endpoint normalization** — `normalize_endpoint()` now appends `/chat/completions` when the configured LLM endpoint omits it, fixing the endpoint footgun that produced a 404 when an endpoint was set to `…/v1` (the v0.5.0 Finding #9 / LLM-1 class, now hardened in-repo).

## [0.5.0] - 2026-06-21

Unified multimodal embedding — **one omni model for text, image, audio, and video** in a single cross-modal vector space, plus an upload-and-embed `/ingest-media` route and the audio/video arms of `/v1/embed`. Where Veda previously needed a text model plus a separate multimodal model, `jina-embeddings-v5-omni-small` now serves all four modalities at 1024-d, so a text query can retrieve audio/video/image records directly (and vice versa). Live-validated end-to-end on real data (OmniDocBench pages, ESC-50 audio, UCF101 video): the full ingest → embed → store → search → rerank → LLM-RAG path works for every modality, with **text↔audio retrieval strong** (dog/rain clips ranked correctly vs ground truth) and **text→video weak** (a model/frame-sampling quality limitation, not a pipeline defect). This release also lands the fixes surfaced by the multimodal E2E campaign (rerank protocol, static-auth enforcement, core-admin RBAC, web egress proxy, two Niriksha frontend bugs, and a batch of correctness/observability fixes). See `documentation/2026-06-21-multimodal-omni-audio-video.md` and `reports/2026-06-21-e2e-report.md`.

### Added
- **Unified omni embedder (`jina-v5-omni-small`)** — a multimodal preset registering ONE model with modalities `[Text, Image, Audio, Video]` at 1024-d. Pointing both `EMBEDDING_*` and `MULTIMODAL_*` at the same omni sidecar gives a single cross-modal space (text/audio/video/image vectors are directly comparable). The multimodal payload builder gained an **audio** arm.
- **`/v1/embed` audio + video** — `POST /v1/embed` now accepts `audio_b64` / `video_b64` (alongside `text` / `image_b64`); `resolve_modality` routes each request to the right modality arm and resolves image/audio/video without hijacking the text default. Response carries `{model, modality, dimension, values, elapsed_ms}`.
- **`POST /v1/collections/{name}/ingest-media`** — a multipart upload-and-embed route for image/audio/video: the file's MIME type selects the modality, the collection's matching `auto_embed` vector field selects the embedding, the raw bytes are stored as a blob, and a record is inserted — in one call. Collection shape: a vector field with `auto_embed { source, modality }` + a `media_blob` Blob field (+ optional `source_path` / `class`). Returns `NO_MEDIA_FIELD` (422) when no `auto_embed` field matches the uploaded modality.

### Fixed
- **Rerank now speaks TEI-style rerankers** — `call_reranker` previously hard-coded the Cohere/Voyage contract (`POST /v1/rerank`, `documents`, `data[].relevance_score`) and returned 404/502 against the deployed `cl-nagoya/ruri-v3-reranker-310m` (a TEI server: `POST /rerank`, `texts`, bare array). The request now carries both `documents` and `texts`, tries `/v1/rerank` then falls back to `/rerank`, and a new `parse_rerank_response` accepts bare-array / `data` / `results` shapes with `relevance_score` or `score`. Both standalone and inline rerank verified end-to-end.
- **`VEDA_AUTH_MODE=static` via env now actually enforces auth** *(security)* — static auth was a silent no-op (`AppState::new()` hardcoded `auth_enabled:false` / empty users / default secret; the env loader couldn't mutate them), so every request bypassed auth and every login 401'd. Construction now seeds users (`VEDA_BOOTSTRAP_ADMIN_*`, `VEDA_STATIC_USERS=user:password:role,…`), reads `VEDA_JWT_SECRET`, and enables auth.
- **Core `/v1/admin/*` routes gated behind `require_admin`** *(security)* — `/v1/admin/{nodes,metrics,jobs,region_topology,replica/safe_ts,cluster/*,…}` were on the shared-auth `protected` router with no authorization layer, so any authenticated user (even a Viewer) reached operator/admin routes. They now sit behind `require_admin` (auth-off deployments unaffected).
- **Visual Search embed call** — Niriksha's Visual Search hardcoded `model=clip-vit-base-patch32` (not in this deployment's registry to `/embed` 400, page broken); it now lets the server auto-select the unified multimodal model.
- **Insights nested-button hydration error** — the Insights event list rendered each row as a `<button>` wrapping the Ack `<button>` (invalid HTML, a React hydration error on every visit); the outer row is now a `role="button"` div with keyboard handling.
- **`.env` loader no longer clobbers explicit env vars** — the loader unconditionally `set_var`-ed every `.env` line, overriding already-exported vars (inverse of dotenv semantics); it now only sets keys that are absent. (This was the root cause of a stale text-only embedding endpoint silently shadowing the omni sidecar.)
- **LLM cost / cache metrics now render from startup** — `veda_llm_cost_usd_total` and the cache hit/miss counters previously never appeared against a local/unpriced model; they are now pre-registered (described + zero-initialized) at startup so per-model series accumulate on top.

### Changed
- **Guardrail default threshold recalibrated for jina-omni** — `DEFAULT_THRESHOLD` lowered 0.80 to 0.65 (paraphrased prompt-injection attacks score ~0.56–0.73 on this embedder), and the guardrail verdict now always surfaces the strongest observed cosine in `score` even below threshold, so sub-threshold near-misses are observable. Mode remains Flag (detect-only).

### Added (web egress)
- **`VEDA_CRAWL4AI_BROWSER_PROXY` compose passthrough** — an env-gated passthrough (`VEDA_CRAWL4AI_BROWSER_PROXY` to `CRAWL4AI_UPSTREAM_PROXY`) so a hardened crawl4ai build can tunnel its (already SSRF-pinned) target through a corporate HTTP-CONNECT proxy on hosts with no direct egress. Empty default = direct dial; the SSRF IP-pin still runs first.

## [0.4.1] - 2026-06-20

Web connector hardening + fixes — follow-ups to the v0.4.0 web stack, plus a live-container e2e (`docker compose --profile web`). A **default-secure SSRF URL guard** now rejects fetching private/internal/reserved addresses (the v0.4.0 "allowlist is a follow-up" gap is closed); the crawl4ai client was pointed at the **real `POST /md` endpoint** (the prior `/crawl` does not exist in crawl4ai's REST API); and `max_pages` is clamped to a server cap. Live-validated against the real `unclecode/crawl4ai` + `searxng/searxng` images: **searxng `web_search`** returned a grounded answer from 8 real engine results, the **SSRF guard** blocked `169.254.169.254` / loopback with **403 `URL_BLOCKED_PRIVATE`**, and the **crawl4ai `/md`** path reached the container and launched headless Chromium (the old `/crawl` 500'd at routing) — a full external crawl could not complete only because this test host's corporate proxy blocks crawl4ai's headless Chromium from egressing (an environment limitation, not a Veda bug). See `documentation/2026-06-19-web-connectors.md`.

### Security
- **SSRF URL guard (default-secure)** — `ingest-url`, the connector `run` path, and the `fetch_url` agent tool now run every user-provided URL through a guard that **resolves the host and checks the RESOLVED IP** (DNS-rebinding-safe), rejecting **loopback, RFC1918, link-local (incl. the `169.254.169.254` cloud-metadata address), and IPv6 ULA** by default. A blocked URL returns **403 `URL_BLOCKED_PRIVATE`** (or a `{blocked:true}` tool result for `fetch_url`) **without crawling**. Tunable via host-suffix `VEDA_WEB_ALLOWLIST` / `VEDA_WEB_BLOCKLIST` and a `VEDA_WEB_ALLOW_PRIVATE=1` escape hatch. This closes the v0.4.0 "allowlist is a follow-up" item.
- **`max_pages` cap** — deep-crawl `max_pages` is clamped to a server cap `MAX_PAGES_CAP=50` (env `VEDA_WEB_MAX_PAGES`) so a request can't ask for a runaway crawl.

### Fixed
- **crawl4ai client uses `POST /md` (not the non-existent `/crawl`)** — the `Crawl4aiClient` targeted a `/crawl` route that does not exist in crawl4ai's REST API; the real endpoint is **`POST /md`** (single `url` + `f:"fit"` → clean markdown). Fixed, with the mock tests corrected to `/md`. (Recursive/deep crawl via the async `/crawl/job` endpoint is a documented follow-up; `deep_crawl` / `max_pages` are accepted but per-URL `/md` is used today.)

### Changed
- **crawl4ai exposure requires `VEDA_CRAWL4AI_TOKEN`** — the crawl4ai container binds loopback-only unless `CRAWL4AI_API_TOKEN` is set (then it binds all interfaces **and** requires the bearer); the compose wires `CRAWL4AI_API_TOKEN: ${VEDA_CRAWL4AI_TOKEN:-}`, which is also Veda's bearer to crawl4ai. So you **must** set `VEDA_CRAWL4AI_TOKEN` to actually use crawl4ai — without it the container is unreachable from Veda even when "healthy".

## [0.4.0] - 2026-06-19

Web Connectors & Agentic Web Search — the in-lane, differentiating answer to Elastic's data-source connectors. Rather than chasing Elastic's 30+ SaaS connectors, Veda ships a self-hosted, privacy-respecting web-RAG stack (crawl4ai + searxng) plus a small connectors framework: ingest live web pages into a collection, let an agent **search → fetch → ground** over the open web, and manage web data sources from Niriksha — all over open-source services you run yourself, with **no external API**. Built on the existing primitives (the chunk → embed → insert path, the agent ToolCatalog, and SavedObjects-backed persistence). Both web services are **opt-in (endpoints unset → clean "not configured"/503, no behavior change)** and the web agent tools are excluded from the default `veda-agent`. Unit/mock-tested (in-test crawl4ai + searxng servers, including a connector `run` that mock-crawls and does a real chunk/embed/insert); **live validation requires `docker compose --profile web`** (not run in CI — the crawl4ai image is large). See `documentation/2026-06-19-web-connectors.md`.

### Added
- **Web ingestion connector (crawl4ai)** — a `Crawl4aiClient` (async `reqwest` → `POST {VEDA_CRAWL4AI_ENDPOINT}/crawl` → clean markdown; opt-in, `None` when the endpoint is unset) and `POST /v1/collections/{name}/ingest-url { url|urls, deep_crawl?, max_pages?, chunker?, ttl_secs? }` — crawl → markdown → a factored shared **`ingest_markdown` helper** (chunk → embed → insert) that `process-document` was refactored to also use (no OCR regression). Records carry `source_url` / `title` / `chunk_index`. Tenant/RLS-scoped; returns **503** when crawl4ai is unconfigured.
- **Agentic web search (searxng)** — a `SearxngClient` (→ `GET {VEDA_SEARXNG_ENDPOINT}/search?format=json`) and two **opt-in** agent ToolCatalog tools: `web_search { query, limit }` (searxng results) and `fetch_url { url }` (crawl4ai markdown, truncated) — so an agent can **search → fetch → ground** over the live web. A built-in **`veda-web`** agent whitelists `web_search` + `fetch_url` + `search`. **Opt-in enforcement:** the web tools are excluded from the default `veda-agent` (the catalog has 15 builtins, but the default agent still resolves to 13).
- **Connectors framework + Niriksha page** — `rest/connectors.rs`: `Connector { id, kind: web|websearch, name, config, enabled }` persisted via SavedObjects (tenant-scoped; `id` optional on create → `conn-{uuid}`). CRUD `GET`/`POST /v1/admin/connectors`, `GET`/`PUT`/`DELETE /v1/admin/connectors/{id}`, and `POST /v1/admin/connectors/{id}/run` (a Web connector crawls its configured URLs into its target collection, reusing the Phase-1 `crawl_and_ingest`). Niriksha `Settings.tsx` gained a **Data Source Connectors** CRUD section (add a web source + "Crawl now") alongside the existing read-only infra-service status.
- **`--profile web` Docker Compose services** — a new `--profile web` adds `crawl4ai` (`unclecode/crawl4ai`) and `searxng` (`searxng/searxng`, JSON output via a mounted `settings.yml`); `VEDA_CRAWL4AI_ENDPOINT` / `VEDA_SEARXNG_ENDPOINT` (+ optional tokens) are wired into the `veda` service, **default empty (opt-in)**.

## [0.3.3] - 2026-06-19

LLM observability follow-ups — two refinements to the v0.3.2 LLM-observability stores. The per-write seal+rebuild that made cache/memory/trace vectors searchable is replaced by **live-growing search** (a major perf improvement: no per-store seal/rebuild), and the LLM **trace store gains a retention TTL** so prompts/responses auto-expire. Live-validated against a running server (a repeated prompt still returns `cache_hit:true`; 15 distinct stores produced **0 sealed segments**, was ~15). See `documentation/2026-06-19-llm-observability.md`.

### Changed
- **Live-growing search replaces per-write seal+rebuild for the cache / memory / trace stores** — `insert_and_index` previously sealed the growing segment and rebuilt the executors (O(collection)) on **every** cache/memory/trace store, which was correct but expensive for high-volume traffic (a tiny sealed segment + a rebuild per write). Stores now `insert_only` into the growing segment (which seals on the normal size threshold), and lookups call `search_live_growing` to brute-force the bounded live growing segment and **merge** those results with the sealed-executor results. Fresh entries stay searchable immediately, with **zero per-write rebuild**.

### Added

## [0.2.3] - 2026-06-12

Two feature cycles landed on 2026-06-12: Elasticsearch-parity text search, then Postgres-extension parity (built Rust-native on Veda's existing primitives — no Postgres extension code was forked). See `documentation/2026-06-12-postgres-parity-features.md` for the Postgres feasibility assessment.

### Added — Elasticsearch-parity text search
- **BM25 analyzer pipeline** — the BM25 index gained a configurable analyzer: char filters (HTML strip / entity mapping), tokenizer, and post-tokenize **stemming** (English Snowball via `rust-stemmers`) + **stopword** removal. The analyzer is applied identically at index and query time (the persisted `AnalyzerConfig` rides alongside `TokenizerKind`), so `fox` matches `foxes` and stopwords/markup are dropped consistently.
- **Phrase / proximity queries** — BM25 postings now carry token positions; `Bm25Index::search_phrase(terms, slop, k)` intersects docs containing all terms and verifies adjacency (slop 0) or within-N proximity, ranking survivors with the existing BM25 score. Exposed as a `match_phrase` query in the gateway DSL.
- **Segment compression** — sealed **stored-field columns** are `zstd`-compressed at seal time (`ColumnarWriter`) and decompressed on read; the mmap'd vector `.vec` files are deliberately left uncompressed to preserve the zero-copy ANN/brute-force scan.
- **True multi-node distributed search** — a gRPC search service exposes `SearchShard` (Phase-1 lightweight `ScoredRecord` ids+scores) and `FetchRecords` (Phase-2 remote full-record fetch). A `RemoteShardSearcher` implements the `ShardSearcher` trait over the existing tonic transport; `DistributedQueryExecutor` registers Local or Remote per shard from `route_query`'s placement, reuses the global top-k merge, and `populate_hit_fields` fetches final top-k records from the owning node when the shard is remote.

### Added — Postgres-extension parity
- **JSONB-style path filtering** — the filter DSL now accepts dotted field paths (`meta.user.tier = "gold"`) that traverse into nested `FieldValue::Json` values via `serde_json::Value::pointer`, coercing the leaf to a comparable scalar. Non-JSON fields and missing paths are unaffected (missing path → no match). Implemented in `veda-query::filter::record_eval::resolve_field`; works on every filter site (search, records, aggregations).
- **Row-level security (RLS)** — a collection may declare an optional `rls_owner_field` at create time (`POST /v1/collections`). When set, the gateway AND-injects `<owner_field> == <jwt-subject>` into the parsed `FilterExpr` on every read (search/get/list) and enforces `owner == subject` on insert; the Admin role bypasses. Injection happens at the AST level (`veda-gateway::rls::inject_owner_filter`) via a new `filter_expr: Option<FilterExpr>` carried on the search requests — the trusted predicate is never round-tripped through an unescaped filter string.
- **Cron-style scheduled jobs** — admin-only scheduler with `POST /v1/admin/jobs` (register/overwrite), `GET /v1/admin/jobs` (list), `DELETE /v1/admin/jobs/{name}`. Jobs carry a cron expression (validated by the `cron` crate; 400 on invalid) and a typed `JobKind` enum (`TtlSweep`, `Reindex`, `Compact`, `Evaluate`) — not arbitrary code. The registry persists to JSON in the data dir and reloads on restart; a single tokio loop ticks and dispatches due jobs (`is_due` is deterministic on an injected `now` for testability). `TtlSweep` is wired to the record-TTL sweeper; `Reindex`/`Compact`/`Evaluate` are registered hooks whose dispatch is stubbed pending later wiring.
- **Record TTL + expiry sweeper** — a reserved record field `_expires_at` (unix seconds) marks a record's expiry. Expired records are excluded at query time from search (`populate_hit_fields` + rerank), `GET /records/{id}`, and `GET /records` via `SegmentManager::lookup_record_at(id, now)`, and are physically purged by `SegmentManager::sweep_expired(now)` driven by a `TtlSweep` scheduled job. `Record::expires_at_secs()` / `is_expired_at(now)` and `veda_core::record::EXPIRES_AT_FIELD` back the convention; the reserved field now persists through segment seal (previously a non-schema field was dropped).
- **Analytics aggregations** — three read-only OLAP endpoints over the columnar store, all honoring the filter DSL (and RLS injection):
  - `GET /v1/collections/{name}/aggregate?field=&metric={count|sum|avg|min|max}&group_by=&filter=` — scalar metric with optional grouping; numeric metrics validate the field is numeric.
  - `GET /v1/collections/{name}/histogram?field=&bins=&filter=` — equal-width numeric histogram (default 10 bins).
  - `GET /v1/collections/{name}/field-stats?field=&filter=` — total/null counts, cardinality, and numeric (min/max/avg) or string (min/max length) summaries.

- 9 LogApplier unit tests; 5 MVCC WAL unit tests; 5 `mvcc_executor_test` integration tests (incl. sealed-segment seal→reopen→search) + 4 segment-manager MVCC durability tests; 4 atomic-create / rollback tests; 4 reindex / alias tests; 3 mvcc_test gateway tests; 1 log_applier gateway test; 3 wan cutover + lag-recovery tests; 2 tonic_log + 2 tonic_wan round-trip tests; 6 store::tests covering aliases + region topology + ts lease.

### Changed
- `ClusterStateMachine::snapshot()` no longer carries `records` / `open_txns`. Metadata snapshot bounded by schema count, not record count.
- `insert_via_log` is now the only data-plane write path. The non-Raft fall-through that writes directly to `SegmentManager` is kept for single-node deployments without log-primary; multi-node operates via the log path universally.

### Removed
- `dark_write_enabled` and the dark-write blocks. Phase B's `VEDA_LOG_DARK_WRITE` knob existed to mirror writes to the log alongside Raft during pre-Phase-C rollout; with Phase E hard-remove the log IS the only path.
- `migrate_persisted_blob` + `build_persisted_blob_for_state` from `veda-coordinator::raft_storage` (no in-process migration to express now that the v0 fields are gone).
- `PendingTxn` struct from `veda-coordinator::store` (transaction state lives in the Percolator `TxnCoordinator`).
- Gateway per-record post-filter for MVCC visibility in `search.rs` — the executor handles every visibility decision precisely.

### Notes
- The metadata Raft snapshot for a workload of 100k collections + 10M records is now bounded under 100 MB (was unbounded; previously grew linearly with record count).
- Backwards-compatible on-disk format: pre-MVCC sealed segments stay byte-identical (no `commit_ts.bin` written when no doc was stamped); pre-Phase-F `raft_state.bin` no longer loads (rebuild from logs or use the pre-Phase-E binary to migrate first).
